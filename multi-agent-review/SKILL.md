# 多 Agent 审查

## 核心规则

开始工作前，先判断用户是否已经明确审查目标。审查目标至少包括要检查的对象和期望判断；是否允许编辑、重点风险或范围边界会影响执行时，也需要明确。用户已经说明清楚时直接继续；用户没有说明、表述模糊或存在关键歧义时，先追问，得到答复后再检查上下文、编辑或启动审查。

审查分两阶段进行：

1. 自审：主 agent 反复审查并修复，直到一次完整自审不再发现新的实质问题。
2. 子 agent 审查：执行同构审查轮次。每一轮都由一个新的独立子 agent 审查最新审查对象。如果该轮发现问题，处理被采纳的问题，并让同一个子 agent 复查最新审查对象，直到该轮不再发现新的实质问题。然后再开启下一轮新的独立子 agent 审查。

只有第一阶段已经完成一次“无新实质问题”的自审后，才能启动子 agent 审查。在子 agent 审查期间，等待该子 agent 返回结果后再编辑被审查对象。

整个审查只在以下情况下停止：一个新启动的子 agent 轮次在最新审查对象上找不到新的实质问题，并且该次干净检查期间及之后没有发生审查对象修改、问题判断变化或材料性用户决策变化。

## 工作流

1. 确定审查目标：审查对象、期望判断，以及会影响执行的编辑权限、重点风险或范围边界。用户提供的信息足够明确时直接继续；信息缺失、表述模糊或存在关键歧义时先追问。
2. 检查足够的本地上下文，以便审查对象并给子 agent 准备审查说明。
3. 完成第一阶段自审，并得到一次无新实质问题的自审结果。
4. 执行第二阶段子 agent 审查轮次，直到满足停止条件。
5. 汇报发现、修复、验证和收敛表。

## 第一阶段：自审

对最新审查对象反复执行自审：

1. 检查正确性、回归、遗漏需求、边界情况、安全/数据丢失风险、性能断崖、可维护性风险、缺失测试。
2. 列出该次检查发现的所有实质问题。
3. 接受有证据支持的问题；拒绝与源码事实或用户意图冲突的问题。
4. 如果允许编辑，则修复被接受的问题，同时保留项目风格和用户已有改动。
5. 如果被接受的问题影响行为，则添加或调整测试。

当一次完整自审不再发现新的实质问题时，第一阶段完成。需要用户决定的问题会阻塞干净完成，直到用户作出决定或改变审查范围/风险决策。

## 第二阶段：子 agent 审查轮次

按以下循环执行：

1. 为当前轮次启动一个新的独立子 agent。
   - 使用可用的子 agent 工具。
   - 对只读代码库、差异、架构或方案审查，使用 `explorer`。
   - 当审查目标不依赖本地代码库时，使用 `default`。
   - 子 agent 角色保持为只读审查；主 agent 负责编辑和协调。
2. 要求子 agent 完整审查最新审查对象，并优先返回问题。
3. 校验返回结果：
   - 必须说明审查了哪个对象/范围。
   - 必须返回具体问题，或明确说明没有新的实质问题。
   - 空白、不完整、无响应、无范围的输出无效。要求同一个子 agent 再返回一次有效响应；如果仍然无效，则结束该轮，重新执行第一阶段，并开启新一轮。
4. 如果新轮次返回了有效的“无新实质问题”结果，并且该轮没有发生修改或材料性决策变化，则停止整个审查。
5. 如果该轮返回问题：
   - 基于证据判断哪些问题被接受、拒绝或仍不清楚。
   - 与同一个子 agent 讨论不清楚或有争议的问题。
   - 如果允许编辑，则修复被接受的问题。
   - 在修复或材料性修改后，对最新审查对象重新执行第一阶段。
   - 将最新审查对象发回同一个子 agent 做完整复查，摘要或差异只作为辅助上下文。
   - 持续使用同一个子 agent，直到它对最新审查对象的最新有效检查明确表示没有新的实质问题。
6. 如果某一轮发现了问题、修改了审查对象、改变了问题判断，或记录了材料性用户决策，则开启下一轮新的独立子 agent 审查。

在只审查不编辑的范围内，未解决的实质问题保留为问题或建议。只有当前范围/风险决策使这些问题变为非阻塞，并且新的独立子 agent 轮次不再发现新的实质问题时，才能干净停止。

## 审查 Prompt

每个新的子 agent 轮次使用这个结构：

```text
审查范围：<文件 / 方案 / 差异 / 行为>。

你是本任务的审查者。你的角色是只读审查；主 agent 负责编辑和协调。

用户意图：
<简要总结>

需要检查的审查对象：
<路径、差异摘要，或粘贴的方案>

请先说明你审查的对象和范围，然后再给出问题或“未发现新实质问题”的结论。根据审查对象类型选择审查标准；常见检查项包括：正确性、需求覆盖、顺序关系、内部一致性、过时表述、触发条件或元数据不匹配、有歧义的停止条件、最终汇报要求、不必要的防御性表述、边界情况、安全/数据丢失风险、性能断崖、可维护性风险、缺失测试。尽量列出本次能发现的所有实质问题。多个问题共享同一根因时可以合并说明，但仍要列出每个可行动的缺陷或风险。先返回问题，按严重程度排序，并使用 `P0`、`P1`、`P2`、`P3` 等标签。包含具体证据，例如“文件:行号”引用或章节名。单独标出问题之外的疑问。如果没有发现新的实质问题，请明确说明。
```

修复或决策后，同一个子 agent 复查使用这个结构：

```text
请完整审查最新审查对象。修复摘要只作为辅助上下文。

你是本任务的审查者。你的角色是只读审查；主 agent 负责编辑和协调。

已接受的修复和决策：
<简短列表>

范围：
<文件 / 方案 / 差异 / 行为>

需要检查的最新审查对象：
<审查对象路径或完整更新内容>

辅助上下文：
<相关差异 / 之前的决策摘要>

请先说明你审查的对象和范围，然后再给出问题或“未发现新实质问题”的结论。先验证已接受的修复，再根据审查对象类型完整审查最新审查对象是否存在新的或仍然存在的实质问题。先返回问题，并提供严重程度标签和具体证据。如果没有发现新的实质问题，请明确说明。
```

## 最终回复

如果审查完成，汇报：

- 按实质问题分组的已修复或已建议处理的问题。
- 执行过的测试或验证。
- 收敛表，字段为：阶段、检查序号、发现问题、有效问题。有效问题指被主 agent 判断为有效，并已处理或采纳的问题。

如果审查无法完成，汇报阻塞原因和最后完成的步骤。
