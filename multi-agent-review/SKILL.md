# 多 Agent 审查

## 核心规则

开始工作前，确认用户是否已经明确审查对象、包含范围、排除范围、审查标准，以及什么算通过、什么算实质问题。信息完整且无关键歧义时直接继续，不重复确认；缺失、模糊或彼此冲突时，先用一个集中问题确认，得到答复后再检查上下文、编辑或启动审查。

默认采用边查边改模式：主 agent 接受有证据支持的问题后，立即修复并验证，再继续审查。未明确限制编辑的审查请求必须视为允许编辑；不得追问编辑权限，也不得按只读处理。用户只说“审查”“检查”“评审”不表示只读。只有用户明确要求不能修改、只做审查、只报告问题或只给建议时，才采用只读模式。

审查分两阶段进行：

1. 自审：主 agent 反复审查并修复，直到一次完整自审不再发现新的实质问题。
2. 子 agent 审查：执行同构审查轮次。每一轮都由一个新的独立子 agent 审查最新审查对象。如果主 agent 接受了该轮的问题，处理被接受的问题，并让同一个子 agent 复查最新审查对象，直到该轮不再发现新的有效问题。然后再开启下一轮新的独立子 agent 审查。

只有第一阶段已经完成一次“无新实质问题”的自审后，才能启动子 agent 审查。在子 agent 审查期间，等待该子 agent 返回结果后再编辑被审查对象。

整个审查只在以下情况下停止：一个新启动的子 agent 轮次在最新审查对象上没有发现被主 agent 独立裁决为有效的新问题，并且该次检查期间及之后没有发生审查对象修改、已接受问题的判断变化或材料性用户决策变化。

## 审查契约

主 agent 在开始审查前，根据用户已经明确的信息建立并遵守以下契约：

- **审查对象**：要判断的文件、变更、方案或行为。
- **包含范围**：需要检查的内容和影响面。
- **排除范围**：明确不检查、不评价和不修改的内容。
- **审查标准**：用于判断的需求、规范、约束和预期行为。
- **判定规则**：什么情况算通过，什么情况算实质问题。

只有用户可以扩大或改变审查契约。主 agent 和子 agent 可以选择任何有助于契约内判断的分析方法和必要上下文，但不能自行增加审查对象、标准或问题类型。范围外观察不作为问题、修复依据或不通过结论；只有它确实阻碍契约内判断时，才作为阻塞项请求用户决定是否扩大范围。修复契约内问题需要修改排除范围中的内容时，先征得用户同意。

## 工作流

1. 建立审查契约。未明确限制编辑时直接进入边查边改模式，不询问编辑权限；仅记录用户明确提出的只读限制。
2. 只检查完成契约内判断所需的上下文，并把同一份审查契约交给子 agent。
3. 完成第一阶段自审，并得到一次无新实质问题的自审结果。
4. 执行第二阶段子 agent 审查轮次，直到满足停止条件。
5. 汇报发现、修复、验证和收敛表。

## 第一阶段：自审

对最新审查对象反复执行自审：

1. 严格依据审查契约检查最新对象，不自行增加标准或范围。
2. 列出该次检查发现的所有契约内候选问题，并指出对应的标准或判定规则。
3. 按“问题裁决”独立判断每个候选问题。
4. 修复被接受的问题，同时保留项目风格和用户已有改动。仅在用户明确要求只读时保留为问题或建议。
5. 如果被接受的问题影响行为，则添加或调整测试。

当一次完整自审不再发现新的实质问题时，第一阶段完成。需要用户决定的问题会阻塞干净完成，直到用户作出决定或改变审查范围/风险决策。

## 问题裁决

子 agent 的结论只是待核验主张。主 agent 必须逐项回到最新审查对象和审查契约独立判断，不得因为 reviewer 的措辞、严重度或信心而默认接受。

一个问题只有同时满足以下条件才接受：

- 位于包含范围内，且不属于排除范围；
- 违反审查契约中的具体标准或判定规则；
- 能说明具体失败、回归或实质风险，而非偏好或泛化建议；
- 有可从最新对象、测试或可靠资料核实的证据。

任一条件不满足就拒绝，并简要记录理由。无法独立核实时，先要求原 reviewer 补充证据或检查反例；仍无法核实就拒绝。范围外建议不转化为新审查目标；推测性风险、纯风格建议、无法对应审查标准的问题和重复问题均不进入修复或最终不通过结论。只有确实需要用户改变契约时才询问用户。

## 第二阶段：子 agent 审查轮次

按以下循环执行：

1. 为当前轮次启动一个新的独立子 agent。
   - 使用可用的子 agent 工具。
   - 对只读代码库、差异、架构或方案审查，使用 `explorer`。
   - 当审查目标不依赖本地代码库时，使用 `default`。
   - 子 agent 角色保持为只读审查；主 agent 负责编辑和协调。
2. 要求子 agent 在审查契约内完整审查最新对象，并优先返回问题。
3. 校验返回结果：
   - 必须说明审查了哪个对象和契约范围。
   - 必须返回具体问题，或明确说明没有新的实质问题。
   - 每个问题必须对应审查契约中的具体标准或判定规则；范围外内容不能列为问题。
   - 修复后的复查必须同时验证已接受的修复，并重新完整扫描最新审查对象，主动检查此前未发现的新实质问题。只检查之前问题的输出无效。
   - 空白、不完整、无响应、无范围的输出无效。要求同一个子 agent 再返回一次有效响应；如果仍然无效，则结束该轮，重新执行第一阶段，并开启新一轮。
4. 如果新轮次没有返回问题，或返回的问题经主 agent 独立裁决后全部被拒绝，并且该轮没有修改或材料性决策变化，则停止整个审查。
5. 如果主 agent 接受了该轮的问题：
   - 修复被接受的问题。仅在用户明确要求只读时保留为问题或建议。
   - 在修复或材料性修改后，对最新审查对象重新执行第一阶段。
   - 将最新审查对象发回同一个子 agent，明确要求它完成两项任务：验证已接受的修复；重新完整扫描最新审查对象，主动寻找此前未发现的新实质问题。摘要或差异只作为辅助上下文。
   - 持续使用同一个子 agent，直到它对最新审查对象的最新有效检查明确表示没有新的实质问题。
6. 如果某一轮接受了问题、修改了审查对象、改变了已接受问题的判断，或记录了材料性用户决策，则开启下一轮新的独立子 agent 审查。

用户明确要求只读时，未解决的实质问题保留为问题或建议。只有当前范围/风险决策使这些问题变为非阻塞，并且新的独立子 agent 轮次不再发现新的实质问题时，才能干净停止。

## 审查 Prompt

每个新的子 agent 轮次使用这个结构：

```text
你是本任务的审查者。你的角色是只读审查；主 agent 负责编辑和协调。

目标是在一次完整审查中尽可能找全真实问题，减少依赖多轮零散发现。

审查契约：
- 审查对象：<文件 / 方案 / 差异 / 行为>
- 包含范围：<需要检查的内容和影响面>
- 排除范围：<不检查、不评价和不修改的内容>
- 审查标准：<需求、规范、约束和预期行为>
- 判定规则：<通过条件和实质问题定义>

需要检查的最新对象：
<路径、差异摘要，或完整内容>

严格依据审查契约完成审查。你可以自行选择分析方法和读取契约内判断所必需的上下文，但不能增加审查范围、标准或问题类型。范围外观察不要列为问题；如果范围外信息确实导致无法完成契约内判断，只把它列为需要主 agent 处理的阻塞项。

尽量一次列出本次能发现的所有真实问题。每个问题必须说明对应的审查标准或判定规则、具体失败结果和证据。先返回问题，按严重程度排序，并使用 `P0`、`P1`、`P2`、`P3` 等标签；问题之外的疑问单独列出。没有发现新的实质问题时明确说明。
```

修复或决策后，同一个子 agent 复查使用这个结构：

```text
请重新完整审查最新审查对象。本次复查包含两项并列任务：
1. 验证已接受的修复是否正确、完整，是否引入回归。
2. 不局限于之前的问题，在同一审查契约内重新检查完整对象，主动寻找此前未发现的新实质问题。

只有完成这两项任务后，才能给出“未发现新实质问题”的结论。修复摘要和之前的问题只作为辅助上下文，不能代替完整审查，也不能限制本次审查范围。

你是本任务的审查者。你的角色是只读审查；主 agent 负责编辑和协调。

目标是在一次完整审查中尽可能找全真实问题，减少依赖多轮零散发现。

审查契约：
- 审查对象：<文件 / 方案 / 差异 / 行为>
- 包含范围：<需要检查的内容和影响面>
- 排除范围：<不检查、不评价和不修改的内容>
- 审查标准：<需求、规范、约束和预期行为>
- 判定规则：<通过条件和实质问题定义>

已接受的修复和决策：
<简短列表>

需要检查的最新审查对象：
<审查对象路径或完整更新内容>

辅助上下文：
<相关差异 / 之前的决策摘要>

严格依据同一审查契约复查，不增加范围、标准或问题类型。请先说明审查对象和契约范围，再分别说明已接受修复的验证结果，以及仍然存在或此前未发现的新实质问题。每个问题必须对应契约中的具体标准或判定规则，并提供具体失败结果、严重程度和证据。只有在验证修复并重新检查完整契约范围后仍未发现实质问题时，才能明确说明“未发现新实质问题”。
```

## 最终回复

如果审查完成，汇报：

- 按实质问题分组的已修复或已建议处理的问题。
- 重要的拒绝项及其不符合审查契约的理由。
- 执行过的测试或验证。
- 按审查契约给出的通过或不通过结论。
- 收敛表，字段为：阶段、检查序号、发现问题、有效问题。有效问题指被主 agent 判断为有效，并已处理或采纳的问题。

如果审查无法完成，汇报阻塞原因和最后完成的步骤。
